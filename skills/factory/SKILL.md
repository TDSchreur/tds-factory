# Factory

<!-- sync, doctor and the skills test find the skills this Skill invokes by the word Invoke followed by a backticked skill name. Keep that phrasing. -->

Walk the work through the Stages below in order. Finish each Stage and tell the user what it produced before starting the next. Move the Run to each next Stage with `tds-factory run transition`; Follow-up may also reopen a delivered Run with `tds-factory run follow-up`. The user can stop or redirect at any Stage.

## Preflight

Check that `tds-factory` is on PATH by running `tds-factory` and checking it exits successfully. If it is unavailable, stop before creating a Run and tell the user to install the Factory CLI globally (for a checkout, run `npm install -g .` there) and make it available on PATH.

Then run `tds-factory doctor --json --agent <your agent>`, which changes nothing, before creating the Run folder. The report has `checks`, the shared checks, and `agents`, one entry per Agent target with its own `checks`. With `--agent` it holds only your entry. The shared checks are the CLI version, the tracker setup (`docs/agents/issue-tracker.md`, `docs/agents/domain.md` and an `## Agent skills` section in `AGENTS.md` or `CLAUDE.md`), the Git `origin` and its default branch, the Verify command and the optional Verify-fast command. Your entry's checks are `binary`, `skills` (the required Skills), `config` (the optional `.factory/config.json`; a bad setting fails with its line) and `review` (the review capabilities). Each check is `pass`, `missing` or `fail`. Ignore your `binary` check, which does not count when you name yourself. If any shared check other than `verify-command` and `verify-fast`, or any other check in your entry, is not `pass`, stop. Do not start the Run and do not create files yourself. Tell the user each failing check and its message, and that the Factory cannot work until they are fixed, then run `/factory` again. Do not suggest a setup command the message does not name. A `fail` of `verify-command` means the command exists but cannot be used (empty, a NUL byte, or a first word that cannot be found): stop and tell the user, never replace it with a guess. A `fail` of `verify-fast` means the optional fast command cannot be used: tell the user and carry on without it. A `missing` Verify command is handled below. The report may also list `notes`, such as merged Runs that still hold a worktree; they never stop a Run. Mention them to the user and carry on.

Then read the project's conventions: `AGENTS.md` or `CLAUDE.md`, the instruction guides it routes to and the canonical specs it lists. Find the verify command in its `## Commands` section (the same line `doctor` read), and the optional `Verify-fast:` line next to it. Record the command in `commands`, the fast command in `fast_commands` when it is usable, and the paths you read in `conventions` when you create the Run. If there is no verify command, tell the user, create the Run now with an empty `commands`, set it to `waiting` while you ask once for the command, and record the answer with `run update`; never guess one.

## Run record

Every Run keeps a Run record that the Dashboard reads. Keep it up to date yourself; do not skip it.

**Start.** Before the first Stage, run `tds-factory run start --data '<JSON>'` in the project being built. Supply a JSON object containing `title`, `agent`, `commands` and `conventions`, and `fast_commands` when the project has a fast command. The command prints the new Run id; keep it for every update. At start it freezes the project review configuration and bundled Skill files from the fetched default-branch revision and the selected target's installed Skills. Projects without configuration and older Runs keep the baseline axes. It creates a unique dated folder and initializes the record, and a Run worktree: a git worktree on a branch named after the Run id, in `.factory/worktrees/<id>`; its path is the `worktree` field of `run.json`. Do all the work of every Stage, Define included, inside the Run worktree, never in the main checkout, so agents in other tabs do not share your files. Every start creates a new worktree from the freshly fetched current default branch of `origin`, including when started inside a linked worktree. If origin cannot be reached or its default branch cannot be determined, start fails; tell the user. `tds-factory` commands write to the main checkout's Run store from either place. If the project is not a git repository or has no commit, `run start` fails: tell the user. An empty `commands` string stands for a verify command the user has not given yet.

**Update.** Use `tds-factory run update --id <id> --data '<JSON>'` for notes on progress; never write `run.json` directly. Supply only changed fields as a JSON object. The command preserves other fields and `created`, refreshes `updated`, validates changes and replaces the record safely. Set `activity` on every update, and often. Once per Stage report `requested_model`, `requested_effort` and, if you can see it, `observed_model`. Update when work becomes `waiting` or is released, when a Ticket completes (`tickets_done`), when the Spec, Tickets or PR links exist, and when the Run is stopped. `run update` cannot change `stage`, `track`, `check_loops`, the verdicts, `verify`, `reviewed`, `accepted`, `worktree` or `base_sha`, cannot set `status` to `done`, and sets `commands` only once, while it is empty; the commands below do the rest. For waiting, see "Waiting on the user". Check command errors and resolve them before continuing.

**Progress commands.** A Run moves with `tds-factory run` commands: `transition`, `verify` (`--fast` while building, the full Verify before Check), `verdict`, `rework`, `sync`, `accept`, `complete` and `clean`, and `track`, `config`, `sweep`, `reviews`, `review`, `follow-up`, `stats`, `inspect` and `repair`. Each checks its prerequisites and refuses with a message saying what is missing; fix that, never work around it. Read `references/progress-commands.md` for what each command does and requires.

Evidence is the Verify result and the verdicts, each tied to the head commit it was recorded for. Project review verdicts are also tied to the recorded base. A commit made afterwards makes Evidence stale, and Finish only accepts current Evidence.

**Gitignore.** If `.factory/` is not covered by the project's `.gitignore`, tell the user to add it. Do not edit `.gitignore` yourself.

**Stop.** If the user tells you to stop, set `status` to `abandoned`.

After changing this skill, re-run `tds-factory install` so the installed copy is updated.
### Schema

`run.json` is one JSON object that the commands maintain for every Agent target; read `references/run-schema.md` for every field and add new fields only when it says so. Record the Spec, Tickets and PR as links only; never copy their content into the Run folder.

### Stage summaries

At the end of each Stage, write a short Markdown summary (a few lines: what was done, what was decided, what is open) into the Run folder: `define.md`, `build.md`, `check-N.md` (one per Check pass, `N` counting from 1, so a Check that sends you back to Build and runs again writes `check-2.md`; it holds a Standards, a Spec, a Security and an Infrastructure section and a Left open list), `finish.md`, and numbered `follow-up-N.md` for each observation. Write plain Markdown only; the Dashboard shows these files as plain text. Never overwrite another Stage's file.

## Waiting on the user

Before you ask the user at each of these points, update the Run with `status` `waiting` and a short `waiting_reason`; the command sets `waiting_on_human`:

- Preflight: no verify command was found, after creating the Run with an empty `commands` and before asking for it.
- Define: a question for the user, the confirmation of the shared understanding after grilling, or on the Fast track the single confirmation, which also covers the track when Define recommended it.
- Check: when any axis is `fail`, or the loop cap is reached with Blocking findings still open, to ask for permission to continue to Finish.

If verification cannot run, set `verification-unavailable` with a `status_reason`; if the agent is interrupted, set `interrupted` with a `status_reason`. Resume either explicitly with `status` `running`. A failed Verify command is not an unavailable one.

When the user answers and the Run continues, set `status` back to `running` before doing anything else; the command clears the flag and the reason, also when the Run ends. If an answer needs no work before your next question, skip that clearing write: set the new `waiting_reason` in the next `waiting` write and write `running` only when real work starts.

## Stage agents

`tds-factory install` also installs the Stage agents `factory-define`, `factory-build`, `factory-check` (read-only), `factory-finish` and `factory-follow-up`, and `factory-interactive-check` for project reviews, per Agent target. You stay the coordinator: you talk to the user, own the Run record, approvals, Check loops and the push. Read `references/stage-agents.md` before you hand work to one.

## Invoked Skills

The Skills named in Define and Build have upstream defaults that conflict with the Flow. This section is the invocation contract: where it and an upstream step disagree, follow this section. Do not ask the user for an approval, confirmation or review that this section or a Stage below already resolved. Follow the Flow through: detailed instructions do not replace Define, never skip a Stage, never work around a refused transition or edit `run.json` directly, and if something blocks a Stage, stop and tell the user. Each `Overrides "..."` quotes the upstream sentence it replaces.

- **to-spec.** Overrides "Check with the user that these seams match their expectations." Choose the seams yourself. Overrides "then publish it to the project issue tracker." The Spec is a Markdown file in `docs/specs/`; do not publish it as an issue and apply no triage label to it.
- **to-tickets.** Overrides "Ask the user:" and "Iterate until the user approves the breakdown." Publish the breakdown without the quiz; the tracker comes from `docs/agents/issue-tracker.md`.
- **implement-spec.** Build runs inline in the Run worktree, on its branch, one commit per Ticket, in dependency order. Overrides "Use an **exploration subagent**" and "Use **implementer subagents**" and "with a **merger subagent**" and "kick off more **implementer subagents**": create no subagents and merge nothing. Overrides "Create the integration branch.": the Run branch is the integration branch, and no Ticket worktrees or extra branches are made. Overrides "open a draft PR": Finish opens the only PR. Overrides "call the Skill tool with `code-review` on the integration branch": no closing review, Check owns it. Overrides "Clean up all **implementer subagent** worktrees.": nothing to clean up. Overrides "If a draft PR exists, mark it ready for review.": Finish owns the PR, and Ticket resolution is left to it through `Closes #N`. The Exit checklist's self-check is inline and is not the closing review: it creates no subagent, does not call `code-review`, and records no verdict or Evidence.

## Tracks

A Run is on the Full track unless the user chooses the Fast track. The Fast track is for bug fixes and tiny changes. Both tracks walk the same Stages and the same transitions; they differ in Define, in the Ticket count and in which Check axes may be `skipped`. Never apply the Fast track silently: either the user names it with `/factory`, or Define recommends it, and the user confirms. Define recommends the Fast track whenever the work meets any of these criteria: a bug fix, a documentation or test-title change, or an expected diff of at most about five files with no new public interface, schema or dependency. The recommendation names the criterion it meets, so the user can confirm or refuse with a reason. Record the answer with `tds-factory run track` while the Run is in Define. If the user says no, record `full`.

Only a clean Check goes on to Finish without asking, on both tracks. The Fast track never lowers that rule.

## Define

Before the steps below, check the criteria in Tracks: a bug fix, a documentation or test-title change, or an expected diff of at most about five files with no new public interface, schema or dependency. When the work meets one, recommend the Fast track and name the criterion in the confirmation. On the Fast track, do this instead of the three steps below. Ask the user exactly one confirmation, with `status` `waiting`: what you understood, the one-paragraph Spec you will write, and the single Ticket; when you recommended the track, include the track. Do not run the interview. For a bug, first Invoke `diagnosing-bugs` to find the cause, and put the diagnosis in the Spec. Then write the Spec as one paragraph in `docs/specs/`, cut exactly one Ticket with `to-tickets`, and publish it without further questions. Update `GLOSSARY.md` or `docs/adr/` only when the change needs it. If the diagnosis shows the work is bigger than a tiny change, say so in the confirmation and recommend the Full track instead.

1. Invoke `grill-with-docs` to settle what has to be done, starting from the work description the user gave with `/factory`; do not ask for it again. Update `GLOSSARY.md` and `docs/adr/` as it goes.
2. Invoke `to-spec` to write the Spec as a Markdown file in `docs/specs/`. Choose the test seams yourself and proceed without asking for seam confirmation or Spec sign-off.
3. Invoke `to-tickets` to cut the Spec into Tickets, published to the Issue tracker named in `docs/agents/issue-tracker.md`, local Markdown when that file names no tracker. Choose the breakdown and publish it without asking the user to review or approve it. Before you ask about a label the tracker needs, look it up: use the label from `labels.ticket` in `tds-factory run config` (default `ready-for-agent`); on GitHub run `gh label list --search <name> --json name` and match the exact name in the output, because a search also returns labels that only resemble it. Ask the user to create the label only when no result matches the exact name, and never run `gh label create` before the lookup. If `gh label create` fails because the label already exists, treat the label as present and carry on. On another tracker, if a label it needs does not exist, ask the user before creating it.

## Build

Build only starts when `tds-factory run transition --id <id> --to build` succeeds, which needs the Spec file named in `spec_link` and a non-empty `tickets`. If it refuses, do not build: say what is missing and continue Define from there.

Work in the Run worktree, on its branch, and commit the Define artifacts first. If the verify command fails for missing dependencies, run the project's normal setup in the worktree. On the Fast track there is one Ticket, so Build is one commit. Invoke `implement-spec`, working test-first (Invoke `tdd`), with one commit per Ticket, until every Ticket is done. Build what the Ticket asks; if a smaller option exists, name it in one line in `build.md`. After each Ticket, raise `tickets_done`, run `tds-factory run verify --id <id> --fast` when the Run has a fast Verify command (otherwise the full `tds-factory run verify --id <id>`) and fix failures before moving on; a fast Verify is not Evidence. List any command that cannot run in this environment (other shell, no container runtime) under "Not run" in `build.md` or `check-N.md`, and never report it as passed. The Build agent works inline and creates no subagents. Skip the closing `code-review` step of `implement-spec`; Check owns the review. When every Ticket is done, run the Exit checklist (read `references/exit-checklist.md`: the project's static checks, a term sweep, the required artifacts, a story trace, a security check and a self-check of your own diff, all inline work that creates no subagent and records no verdict), then run `tds-factory run sync --id <id>` so Check reviews the code on top of the current default branch, run the full `tds-factory run verify --id <id>` (never `--fast`) again and fix failures, then move on with `run transition --to check`.

## Check

Commit everything, then run the full `tds-factory run verify --id <id>` (never `--fast`). In one pass, review those committed changes on the four baseline axes (after a Rework, see the carried-over verdicts below), each in its own fresh read-only subagent so the reviewer did not write the code. Report each axis separately and never merge them. If a fresh read-only reviewer for an axis cannot be started, do not review that axis yourself and record no verdict for it: set the Run to `verification-unavailable` with a `status_reason` naming the axis, and tell the user. Resume with `status` `running` only once a reviewer is available. Run the baseline axes on every Run; Infrastructure is the baseline axis that may be `skipped`. Run each project review according to its frozen applicability.
On the Fast track Standards and Security are required; the Spec axis still runs by default, and you may record it `skipped` when the one-paragraph Spec leaves nothing to review the code against. Infrastructure and project reviews follow the same rules as on the Full track.

Invoke `code-review` for the Standards and Spec axes; it runs one subagent for each. Invoke `security-scan` for the Security axis, in a third subagent. Scope `security-scan` to the files in the same diff `code-review` uses. Give the Standards subagent every instruction guide from `conventions` whose `applyTo` globs match the changed files, and have it flag a change that leaves the canonical spec for that area stale when the changed behavior is documented there: a stale canonical spec is a Blocking finding. Give the Security subagent the project's "Universal safeguards" text from the conventions file, to check explicitly next to the generic patterns. A project with no guides or safeguards is reviewed as before.
Record each baseline axis result with `tds-factory run verdict`. Every axis needs a verdict. An axis with no verdict in `run.json` after the pass is a Blocking finding: run that axis again.
Read `references/check.md` before the pass: it holds the inline assignment for the reviewers, the Infrastructure axis, project reviews, what a Blocking finding and a Left open item are, the pass after a Rework (carried-over verdicts) and when a Check is clean. In short: ask every reviewer for a severity and basis per finding; only a Blocking finding sends the Run back to Build with `tds-factory run rework --id <id>`, and all axes share one loop count: go back at most 4 times; only a clean Check continues to Finish without asking, and when Blocking findings remain or the loop cap is reached, set the Run to `waiting` with a `waiting_reason` and ask the user for permission to continue to Finish.

## Finish

Start with `tds-factory run transition --id <id> --to finish`. Invoke `pr` to prepare the pull request. If the project has a PR template at `.github/pull_request_template.md`, `.azuredevops/pull_request_template.md` or `docs/pull_request_template.md`, pass it to `pr` and fill it in, including its Infrastructure checklist from the `infrastructure` verdict and its Documentation checklist from the stale-spec check; otherwise keep the layout `pr` produces. Then Invoke `unslop` on the PR title and the prose of the body, and leave diagrams, diffs, code blocks, Evidence output and the template's bold labels as they are. Save the cleaned draft as plain Markdown in `pr.md` in the Run folder. The description has a "Left open" section, filled from the `check-N.md` of the last Check (axis, severity and basis per item, or "none"; summarise a security item without exploit details or secret values, because the description is public); `finish.md` repeats the list. Finish does not wait on the user for it. When the tracker is GitHub, the PR body lists `Closes #N` for every Ticket; otherwise it lists the Ticket paths and has no `Closes` lines. Push the branch and open the PR. If `pr` is already recorded, push the new head to the same branch and update that PR; do not open a second PR. When the PR is handled, run `tds-factory run complete --id <id>` after setting `pr`. Once the user has the PR merged, `tds-factory run clean --id <id>` from the main checkout removes the Run worktree and branch; never run it from inside the worktree.

## Follow-up

When asked to address PR feedback after Finish, read `references/follow-up.md` and follow it. The Check and Follow-up Reworks share the cap of four.

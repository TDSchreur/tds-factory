# Define on the Fast track

Before the steps below, check the criteria in Tracks: a bug fix, a documentation or test-title change, or an expected diff of at most about five files with no new public interface, schema or dependency. When the work meets one, recommend the Fast track and name the criterion in the confirmation. On the Fast track, do this instead of the three steps below. Ask the user exactly one confirmation, with `status` `waiting`: what you understood, the one-paragraph Spec you will write, and the single Ticket; when you recommended the track, include the track. Do not run the interview. For a bug, first Invoke `diagnosing-bugs` to find the cause, and put the diagnosis in the Spec. Then write the Spec as one paragraph in `docs/specs/`, cut exactly one Ticket with `to-tickets`, and publish it without further questions. Update `GLOSSARY.md` or `docs/adr/` only when the change needs it. If the diagnosis shows the work is bigger than a tiny change, say so in the confirmation and recommend the Full track instead.

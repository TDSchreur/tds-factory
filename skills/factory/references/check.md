# Check details

Read this before a Check pass.

**Inline assignment.** Once per pass, after the Verify run, collect `git diff <base_sha>...HEAD`, the changed file list (`git diff --name-only <base_sha>...HEAD`), the Verify summary (command, head, exit code and time), the output of `tds-factory run sweep --id <id>` for the Standards reviewer together with the Sweep paragraph of `build.md` (the reviewer checks the hits it judged unaffected), and any command output an axis needs, and put them in each reviewer's assignment (inline, or in one file in the Run folder, named in the assignment, that the reviewer reads first when the assignment is too long to carry them); the reviewers cannot run `git`. They start from that diff and open other files only to follow a reference (a function the diff calls, a document it links, a search for stale text). When the diff is larger than about 40 KB, pass the file list and the per-file diffs up to that size, most important files first, and name the files left out so the reviewer reads those itself. The reviewers stay read-only and fresh.

The Infrastructure axis runs in a fourth fresh read-only subagent, with no new Skill, when the diff changes `*.bicep`, `*.bicepparam`, `bicepconfig.json`, files under `Pipelines/`, `azure-pipelines*.yml` or `*.pipeline.yml`; otherwise record `skipped` with `run verdict`. It runs `bicep build` and `bicep lint` with the project's `bicepconfig.json`. If private modules cannot be restored, it reports "not validated" with the reason and the verdict is `fail`, never `pass`. It runs a what-if only when Azure credentials and a documented target exist, and it must never deploy; a what-if that is not run because credentials or a target are missing is reported as not run. It checks changed pipeline YAML for plaintext secrets, unpinned task or template versions and missing approval gates on production stages, and checks the project's stated invariants (for example no Blob soft delete).

For project reviews, read the frozen plan from `tds-factory run reviews --id <id>` after committing. For each nonmatching review, record `{ "verdict": "skipped" }` with `tds-factory run review`; the command records the reason. For each applicable review, materialize the frozen Skill with `run materialize-review --id <id> --axis <axis>` and pass that directory, diff, report contract and applicable runtime setup to a fresh independent reviewer. Use `factory-check` for `source` reviews; it can read the frozen Skill but cannot run commands. Use a fresh `factory-interactive-check` for `interactive` reviews; it may start a local/test app and use a browser, and saves evidence only in the Run folder. It must not edit implementation files, deploy or use production data. Compare worktree status before and after; if it changed, preserve the changes and stop for reconciliation. The coordinator owns Run updates and records reports with `run review`; do not execute a live Skill instead of the frozen copy. Read the installed `add-project-review` Skill's `references/project-reviews.md` for the report and evidence contract. An interactive pass needs browser evidence; missing tools, prerequisites, the materialized Skill or an independent reviewer sets `verification-unavailable` with the review ID and a recovery reason, never a pass. When available again, resume with a fresh reviewer. Record project review findings and skip reasons in `check-N.md`.

Ask every reviewer, in its assignment, to report each finding with a severity (CRITICAL, HIGH, MEDIUM, LOW or INFO) and the standard, Spec requirement or `judgement` it rests on. A **Blocking finding** is a violation of a documented standard that names the rule (a "must" or "never" in the conventions, the guides, the glossary's Avoid terms or a canonical spec), a CRITICAL, HIGH or MEDIUM security, infrastructure or project review finding, or a Spec requirement that is missing or wrong. A stale statement in a document that describes current behavior (the README, the usage and install guides, the instruction guides, `GLOSSARY.md`, an accepted ADR or a canonical spec listed in the conventions) is a violation of a documented standard; the same statement in a historical Spec in `docs/specs/` that is not canonical is not. Behavior the Spec did not ask for is Left open unless it contradicts a requirement or an "Out of scope" statement. A CRITICAL, HIGH or MEDIUM security, infrastructure or project review finding is Blocking whatever its basis, also when it names no documented standard. Everything else is **Left open**: LOW and INFO items, and every code smell and style or design judgement, which never go above LOW. Apply the reviewer's severity; never raise a LOW to a Blocking finding, and write any disagreement in `check-N.md`. An axis verdict is `fail` only with a Blocking finding, and an axis with only Left open items is `pass`. Write the Left open items in `check-N.md` with their axis, severity and basis.

If there are Blocking findings, go back to Build with `tds-factory run rework --id <id>` and fix them (the security report only proposes patches; Build applies them), then verify and review again; the review of an earlier head no longer counts, except for a Carried-over verdict. In that next pass give each reviewer the previous findings and the rework diff: it confirms each earlier finding is fixed and reviews the rework diff in full. For Security and Infrastructure first run `tds-factory run verdict --id <id> --axis <axis> --value <the earlier value> --carried`; the command keeps the earlier verdict for the current head only after a text-only Rework, and it alone decides: documents only (Markdown in `docs/`, changelog fragments, README), never code, tests, Skills, agents, instruction files, hidden files or links, with a rename counting as both of its paths; its refusal names the files that changed, and you review the axis only when it refuses. Standards and Spec are always reviewed again. All axes share one loop count: go back at most 4 times, plus any extra loops the user granted.

Left open items never stop a Clean Check. Only a clean Check continues to Finish without asking, and `run transition --to finish` refuses anything else. A Check is clean when every applicable axis verdict is `pass`, with Infrastructure and nonmatching project reviews allowed to be `skipped`, the verdicts and a passing Verify result are all recorded for the current head, and the worktree has no uncommitted changes; an axis with no verdict, or a changed infrastructure file that is not validated, counts as `fail`. When Check would otherwise move on (no Blocking finding is left, or the loop cap is reached) but the Check is not clean or Blocking findings are still open, report what is still open, set the Run to `waiting` with a `waiting_reason` and ask the user for permission to continue to Finish, listing the open axes and findings. Continue only after an explicit yes, in the chat. If the user accepted on the Dashboard, the Run is already `running` and `accepted` is recorded for the current head: tell the user you saw it, treat it as their yes and only add the decision to `finish.md`. Otherwise set the Run back to `running`, record the decision with `tds-factory run accept` (the open findings and the decision) and in `finish.md`, then move on. New commits void the accepted decision. On a no, or if the user tells you to stop, set `status` to `abandoned`.

**Extra loop.** When the loop cap is reached with Blocking findings open, you set the Run to `waiting` and ask for permission to continue to Finish. The user may instead grant one extra Check loop on the Dashboard (`extra_loops` in `run.json`, raised only by the Dashboard, never by you and never from the command line). When the user tells you in the chat that they did, or you see `extra_loops` raised and the Run `running` again, that is their decision to go back to Build once more: run `tds-factory run rework --id <id>` and fix the Blocking findings, and do not ask again for permission to continue to Finish. Never edit `extra_loops` and never try to raise the limit another way.

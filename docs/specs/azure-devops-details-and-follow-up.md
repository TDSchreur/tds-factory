# Azure DevOps: Check PR details and Follow-up Fix

## Problem Statement

For an Azure DevOps pull request, Check PR shows only state, draft and merge conflicts, and the Dashboard offers no Fix button; `tds-factory run follow-up` refuses with "Follow-up does not support Azure DevOps yet" ([ADR 0034](../adr/0034-the-dashboard-checks-and-fixes-a-pr-but-never-merges.md), [Dashboard: Check PR and Fix](dashboard-check-pr.md), [Dashboard: Azure DevOps pull request status](dashboard-azure-devops.md)). A user whose repository lives in Azure DevOps cannot see which build or review thread blocks the PR, and cannot send the agent back to fix it. This is [issue #503](https://github.com/TDSchreur/tds-factory/issues/503).

## Solution

The Azure DevOps adapter (`src/pr-azure.js`) reads what GitHub's adapter reads: failing and pending checks, unresolved review threads and merge conflicts, all read-only through `az`. It also gains `strictViewFlow` and `observeFlow`, so Follow-up, the Dashboard Fix buttons, "Grant extra loop and fix" and `/factory continue <run id>` work for Azure DevOps with the rules of ADR 0034: one scope and one Rework at a time, no replies and no thread resolution on the host, review text as untrusted data. The decision is recorded as an addendum to [ADR 0020](../adr/0020-pr-providers-sit-behind-one-seam.md); no new ADR is needed because it follows ADR 0034 and the seam's `can(url, operation)` rule and is easy to reverse.

## User Stories

1. As a user with an Azure DevOps PR, I want Check PR to list each failing check by name with a link, so that I can open the build.
2. As a user, I want pending checks listed, so that I know to wait.
3. As a user, I want each unresolved review thread listed with its file path, a shortened first comment and a link, so that I can judge it without leaving the Dashboard.
4. As a user, I want a failing build policy and a failing status that outside CI posted to the PR to both count as failing checks, and a pending one of either kind as pending, so that the drawer matches what blocks the PR.
5. As a user, I want threads that Azure DevOps creates itself (votes, pushes, policy updates) and threads that are fixed, closed, "by design" or "won't fix" left out, so that only real open review work is listed.
6. As a user, I want review text and check names shown as plain text, cut to the same lengths and capped at the same numbers as for GitHub, with only `https` links, so that a hostile comment cannot inject markup or script.
7. As a user, I want a **Fix conflicts**, **Fix checks** and **Fix comments** button next to the matching problem of an Azure DevOps PR, so that I choose what the agent works on.
8. As a user, I want a Fix click, "Grant extra loop and fix" at the Check loop limit, one Rework at a time and the refusals (worktree cleaned, uncommitted changes, head differs from the PR head) to work as for GitHub, so that the host makes no difference.
9. As a user and as an agent, I want `tds-factory run follow-up --id <id> --scope conflicts|checks|comments` and `/factory continue <run id>` to work for an Azure DevOps PR.
10. As an agent, I want a `comments` Rework to never post replies or resolve threads on Azure DevOps.
11. As a maintainer, I want every new `az` call read-only, the existing test that pins "no write subcommand" to keep passing, and project and repository GUIDs (never names decoded from the link) to reach the command line, so that nothing writes to a live repository and Windows' `cmd.exe` never sees decoded text.
12. As a maintainer, I want tests to use output recorded from the sandbox repository `Kahoot` and never call `az`.

## Implementation Decisions

- **Seams.** The PR provider seam is unchanged: `details(url)` of the Azure DevOps adapter returns the existing `PrDetails` shape (state, draft, conflicts, failing and pending checks with totals, threads with total), and the adapter adds `strictViewFlow(url, cwd)` and `observeFlow(url, head, cwd)` returning what GitHub's return (`PrView & { headRefOid }` and a `FollowUp` snapshot). `can(url, 'strictViewFlow')` then turns true for Azure DevOps and the Fix route, `canFix` in `dashboard/model.js` (no longer `prHost === 'github'`; still false when unreadable or abandoned) and Follow-up follow from it. The seam gets no new operation.
- **Shared helpers.** The sanitising and capping that `src/pr-github.js` holds today (`cut`, `link`, `NAME_MAX`, `PATH_MAX`, `COMMENT_MAX`, `LINK_MAX`, `THREADS_MAX`, `CHECKS_MAX`) move to one module both adapters import, with no change of behaviour for GitHub.
- **Unresolved thread.** A thread is unresolved when its status is `active` or `pending` and it is a person thread: it has at least one comment of `commentType` other than `system` and carries no `CodeReviewThreadType` property (those mark vote, push and policy-update threads). Threads with status `fixed`, `closed`, `byDesign`, `wontFix` and deleted comments are left out. The path is the thread context's `filePath` (empty for a thread on the whole PR); the first comment is the first non-deleted comment; the link is `<PR url>?discussionId=<thread id>`.
- **Checks.** Failing checks are the blocking policies `rejected` or `broken` (as `parseStatus` already decides, with the same exclusions of reviewer policies and the merge strategy policy) plus PR statuses with state `failed` or `error`; pending are policies `running` or `queued` plus statuses `pending`. Only the latest status per `context` (name and genre) counts, and statuses of state `succeeded` or `notApplicable` are not checks. A build policy's link is `https://dev.azure.com/<org>/<project>/_build/results?buildId=<id>`, built from the policy's `context` (the organisation and the project from the PR link and the build id as an integer, nothing taken from free text); a status's link is its `targetUrl`, `https` only. The status line of `statusAsync` and `parseStatus` keep their present meaning; the statuses join the checks result there too so the card and the drawer agree.
- **Conflicts.** `mergeStatus` `conflicts` is true, `succeeded` false, anything else (`queued`, missing) is null in details and "no finding" in `observe`, as GitHub's UNKNOWN is.
- **Calls.** Threads and statuses are read with `az devops invoke --area git --resource pullRequestThreads` and `--resource pullRequestStatuses`, `--route-parameters project=<guid> repositoryId=<guid> pullRequestId=<id>`, `--api-version 7.1`, the validated `--organization`, `--output json` and `--only-show-errors`. The two GUIDs come from the `az repos pr show` output (`repository.id` and `repository.project.id`, checked as GUIDs and compared with the names the link carries by the existing `belongsTo`), never from names decoded from the URL, so only fixed flags, GUIDs and the numeric id reach `cmd.exe`; `launch` keeps refusing anything else and accepts only the one extra character that `name=value` needs, with a Windows test. All calls are GET: no `--http-method` other than the default, and a static test that `invoke` is only ever followed by those two resources.
- **Failures.** The failure codes of the adapter stay (`az-missing`, `az-extension-missing`, `az-not-signed-in`, `rate-limited`, `error`); a shape that is not what the fixtures show throws `error`. The paging limits mirror GitHub's: at most 50 listed and the total counted; the threads response has no paging, so a response with a continuation token is treated as complete for what it returned and the total says so.
- **Follow-up.** `observeFlow` reads at the head the PR has (`lastMergeSourceCommit`) and throws "Azure DevOps PR head changed during Follow-up" when `lastMergeSourceCommit` differs from the `head` it is given, like GitHub's; it reads the PR again after the last read and throws the same error when the head moved meanwhile. Check names and thread paths in the snapshot are cut to the caps of `src/pr-text.js` (the comment bodies stay whole, as for GitHub, and so does the number of threads). The text of an `az` failure that reaches an error is capped at 500 characters with control characters replaced by spaces. A response with a continuation token counts as complete and the total says so. It returns the `FollowUp` snapshot: `conflicts`, `checks` (policies and statuses), `failures`, `pending` and `threads` with their person comments as untrusted text (thread ids as strings). `strictViewFlow` returns state and a head that must look like a commit id. `src/run-follow-up.js` stops assuming a GitHub link: its "needs a GitHub PR URL" messages name no host, and the PR number is read through the adapter's link, not by splitting a GitHub path. The loop cap, clean-worktree check and Rework count are unchanged. A completed PR ends Follow-up as Done, an abandoned one refuses, as for GitHub.
- **Dashboard.** The Fix route, the guard, the grant and the one-Rework rule are host-neutral already ([ADR 0034](../adr/0034-the-dashboard-checks-and-fixes-a-pr-but-never-merges.md)); only the page's offer changes (`canFix`) and the texts that name GitHub for Fix.
- **Documents.** `GLOSSARY.md` (already updated: **PR provider**), `docs/dashboard.md` (the Azure DevOps section, the Check PR and Fix text, the "Follow-up does not support Azure DevOps yet" line), ADR 0020 (an addendum: the adapter's new operations, the two `invoke` reads, the shared sanitising module, and replacing "has no `strictView`, `observe`..."), ADR 0034 (its Azure DevOps paragraph rewritten to the end state), `docs/specs/dashboard-azure-devops.md` (its Capabilities, UI, User Story 7, 8 and Out of Scope lines about Fix and Follow-up), `docs/specs/dashboard-check-pr.md` (its Azure DevOps lines), `docs/install.md` (the Azure CLI row says what else `az` is used for), `dashboard/help.js` (the Fix entry says "GitHub pull request"), `docs/development.md` (the PR provider paragraph if it says Azure DevOps cannot follow up), `skills/factory/references/progress-commands.md` and `run-schema.md` (say "recorded GitHub PR" and "latest GitHub observation"; both are host-neutral now) and the `skills/factory` copies kept in step (ADR 0001), the usage text of `bin/tds-factory.js` if it names GitHub for `follow-up`, and a changelog fragment `changelog.d/azure-devops-details-and-follow-up.md`. The Documents Sweep terms: Azure DevOps, GitHub-only, "Follow-up needs a GitHub", canFix, az devops.
- **Fixtures.** Threads and statuses are recorded from a throw-away PR in the sandbox repository `Kahoot` (project `Projects`), which is abandoned afterwards, into `test/fixtures/pr-status/azure/` as `*.threads.json` and `*.statuses.json`, anonymised as that folder's README says and listed in it. A failing build policy cannot be recorded (the sandbox has no pipeline), so the failing-policy fixtures are derived from a recorded one and marked "not recorded as is".
- **Build or borrow.** No new parser of untrusted text: sanitising reuses GitHub's `cut` and `link`; no dependency.

## Testing Decisions

- Adapter tests with the injected `run`, as in `test/pr-azure.test.js`: details from each fixture (threads of every status and type, system threads, deleted comments, statuses in every state with several per context, failing and pending policies, conflicts, merged and abandoned PRs, caps and totals, hostile text and non-`https` links), `observeFlow` snapshot and head mismatch, `strictViewFlow` shape, every failure code, and the argument lists (GUIDs, not names; GET only; `launch` on `win32`).
- Static: the existing "only the adapter runs `az`, no write subcommand" test passes unchanged; a new one pins the `invoke` resources.
- Follow-up tests (`test/run-follow-up.test.js`) with an injected Azure provider: each scope sends only its findings to Build, loop cap, grant, merged, refusal texts without GitHub wording.
- Dashboard tests: `canFix` true for an Azure DevOps PR, the Fix route succeeds and refuses as for GitHub, and a browser test that the drawer lists Azure DevOps failing checks and threads as text and shows the Fix buttons.
- Fixture tests: the anonymised fixtures hold no e-mail address, tenant or identity id.

## Out of Scope

Any write on Azure DevOps (replying to or resolving threads, voting, completing, commenting); Azure Boards; the `visualstudio.com` link; paging of threads beyond what one response returns; recording a real failing build policy; merging.

# Choose install destinations and clean up deselected copies

## Problem statement

`tds-factory install` currently defaults to installing into every Agent target. Users need to choose where the Factory is installed, including multiple Claude directories, and keep those choices for later confirmation. Leaving old Factory copies in a deselected directory can make an agent continue loading outdated Skills. Removing arbitrary files would risk users' own data and edits.

## Solution

Make `tds-factory install` ask for an Install selection and reconcile the result with Factory-owned installations. Discover `.claude`, `.claude-*` and `CLAUDE_CONFIG_DIR`, allow other Claude paths, and identify legacy installations. Remember global and per-Project choices separately. Cleanup is permitted only after the command establishes the filesystem trust boundary required by ADR 0037. Unsupported or unverifiable environments fail before any installation, cleanup or record change, with an actionable explanation.

This Run implements the direct install command. Issue #568 separately handles the ordering and options needed by `update` and both Bootstrap installers; it must not claim those entry points are complete merely because they invoke `install`.

## User stories

1. As a new user, I want no destination selected silently, so that the Factory installs only where I choose.
2. As a Claude user with `.claude` and `.claude-work`, I want separate choices, so that I can install into either or both.
3. As a Claude user with a nonstandard directory, I want to enter its path, so that it can receive the Factory.
4. As a returning user, I want my saved selection shown for confirmation and newly discovered folders left unselected.
5. As an existing user, I want legacy Factory-owned copies shown as existing, so that I can choose whether to keep them.
6. As a user deselecting a destination, I want its Factory-owned copies removed and edited content backed up, while unrelated files remain untouched.
7. As a Copilot user, I want its dedicated Skills and Stage agents installed independently of Claude and Codex.
8. As a Project user, I want the Project's selection and reconciliation kept separate from global and other Project installations.
9. As an unattended user, I want to name the complete desired selection or explicitly reuse saved choices, rather than falling back to all agents.
10. As a user who cancels or previews, I want no changes to Skills, Stage agents, saved selection or backups.
11. As a user whose prior Claude directory is unavailable, I want it preserved and the selection change refused until its state can be established.
12. As a user on a filesystem whose ownership and access permissions cannot be verified, I want an explanation and no partial installation or cleanup.
13. As a user whose backup fails, I want edited content retained and the failure reported, rather than losing my changes.
14. As a user of the existing `--force` and `--project` options, I want their documented scope retained and applicable to the selected destinations.
15. As a maintainer, I want real terminal and OS-specific permission tests, so the same interaction and trust rules are checked on supported systems.

## Implementation decisions

- Use the merged selection planner, `cleanupDestination` and selection-record writer as the seams for discovery, selection and reconciliation. Extend the installer interface as needed for individual Claude directories and for Copilot's dedicated Skills destination. Do not silently pass `trustedPaths: true`: its precondition must be established first for every operation that needs it.
- In an interactive terminal, show each discovered candidate by Agent target and concrete path, with legacy ownership and previously saved choices distinguishable. The first selection is empty; saved choices are preselected for explicit confirmation and newly discovered candidates are not. Offer a way to add an explicit Claude path. A user can select several destinations; an empty/cancel answer exits without mutation. Output and path displays must not allow terminal control characters to forge prompts or output.
- Existing single-agent `--agent` invocations remain valid and represent the complete desired selection. Accept comma-separated Agent targets via `--agent`, repeatable `--claude-dir PATH` for explicit Claude configurations, and `--reuse-selection` to explicitly reuse the saved selection. Document exact flag combinations in the command help and integration tests. Explicit `all` is an affirmative choice, never the default. Validate incompatible flags and missing saved selections before changing files. A noninteractive call without an explicit choice or reuse option fails with an actionable command example. The complete desired selection governs removal; a previously selected or legacy installed destination that is deselected is reconciled, subject to the unavailable-directory rule.
- Interactive input must work when POSIX stdin contains the downloaded Bootstrap script: use the controlling terminal when available and never read the script stream as an answer. PowerShell 7 and Windows console execution must be tested on Windows; fail clearly when no usable terminal exists. Do not hang waiting for input after EOF or cancellation. The update/bootstrap changes in #568 must account for the CLI install or npm upgrade already occurring before the prompt.
- Each install has global or one Project scope. Save records outside shared source-controlled Project files, isolated per Project and global selection. A saved record never authorizes deletion by itself. Preserve temporarily unavailable selections, and reject malformed or ambiguous records and path aliases before mutation. Use a distinct private backup root that does not overlap Skills or agents destinations.
- Before the first write, build the complete desired set and all legacy and saved destinations to remove. Validate every affected Skills and agents directory, record path, backup root and their existing ancestors. Resolve unsupported or untrusted paths before installing, deleting or saving anything. Preview the selected writes, removals and backup operations. Require all backup work for a destination to finish before removing any of its owned content; preserve unrelated files and linked targets. If any later I/O fails, report partial work accurately and retain recoverable backups and enough prior selection information for a safe retry; never claim an unperformed cleanup succeeded.
- Establish a trusted-path mechanism before invoking cleanup or record writes. Trust only the current user and operating-system administrators; privileged or otherwise trusted principals acting maliciously are outside this boundary. Inspect every existing component from the filesystem root to each destination, record and backup, plus all existing affected data. Reject symbolic links, unexpected object types, identity changes, shared writable ancestors, incomplete inspection and unsupported filesystems before any mutation. Create missing directories with at most `0700` and files with at most `0600` under a verified parent, including installer staging and Stage agent files, so inherited POSIX default ACLs cannot grant write access; recheck identities before use. This conservative policy intentionally refuses some legitimate installations; report the specific obstacle and preserve the existing selection.
- **Linux adapter:** use Node `lstat`, ownership/mode and `statfsSync` with a narrowly enumerated allowlist of local Linux filesystems whose POSIX ACL semantics are verified by real tests. Require every component and affected object to be owned by the current user or root with group and other write bits clear. Linux POSIX ACL's mask limits named users and groups to the group mode bits, so this rule excludes their write access on supported filesystems. Reject unknown, network, sticky/shared or otherwise unsupported mounts. Test named ACLs and masks with real `setfacl`, including default ACLs and newly created paths; do not infer identical behavior on other operating systems.
- **Windows adapter:** invoke a fixed, shipped PowerShell 7 adapter without a shell or interpolated command text, using .NET structured owner SIDs and raw security descriptors. Walk inherited and explicit ACEs and accept only fully understood descriptors; reject null DACLs, unknown ACE forms, untrusted owner or any untrusted allow granting write, child creation/deletion, DELETE, WRITE_DAC or WRITE_OWNER, even if a deny might offset it. Treat the current-user SID, LocalSystem, built-in administrators and the Windows Modules Installer service as trusted operating-system identities; verify the actual account and descriptor identities. Reject reparse points, remote or unverified volumes, missing PowerShell and inspection errors. Both child DELETE and parent FILE_DELETE_CHILD matter. Test with real Windows ACLs and inherited entries. No localized command-output parsing.
- An inherit-only Windows ACE does not apply to its own directory. Inspect it wherever the operation may create a child; on other ancestors, inspect the actual ACL of each existing descendant instead. A grant limited to adding a child to an ancestor also cannot replace an existing, independently verified child: still reject deletion, ACL or ownership control of that ancestor, and all unsafe grants on the nearest existing parent of any missing destination. Never use these distinctions to skip verification of a destination or of an existing descendant.
- **macOS adapter:** call the absolute `/bin/ls` with shell-free arguments `-lde` and one exact path in a sanitized, fixed-locale environment. Accept only the strictly validated, single-record format indicating no ACL; reject `+`, any ACL entry (including deny-only), ambiguous output, unsafe path names, stderr, command errors and unexpected formatting. Independently verify trusted owner and non-writable group/other permissions for every component. Accept only a proven local filesystem with ownership enforcement enabled; if the implementation cannot prove mount type and ownership enforcement using a reliable OS mechanism, refuse the path. Apple documents `ls -le` and the ACL indicator, but this adapter and the mount check are not validated here: real macOS tests must establish that unsupported ACL/volume cases cannot produce a false negative before macOS is claimed supported. Do not substitute permission bits alone.
- **Platform validation gate:** the working environment is Linux only; no PowerShell or real Windows/macOS runtime is available. Linux fixtures can validate only the actual filesystem and kernel on which they run. Windows and macOS adapters and all claimed supported filesystem cases require real platform CI, including inherited and deny-only ACLs, untrusted access, names that could confuse command output, symlink/reparse swaps, disabled ownership and missing runtime handling. Until the relevant evidence passes, affected mutations fail closed and that platform must not be advertised as supported. No new third-party native dependency is selected; `@openclaw/fs-safe` does not itself establish trusted roots and is not a substitute for these checks.
- Add bounded, real Linux, macOS and Windows platform checks to CI when those platforms are claimed supported. The Linux test suite may simulate adapter errors and hostile ACLs, but mocks do not replace real platform tests. The project currently uses only Ubuntu runners for its package/unit matrix. PowerShell scripts and workflows require their repository-specific linters and instructions.
- **Documents:** update `docs/install.md`, `README.md`, `docs/development.md`, `docs/usage.md` where applicable, `docs/specs/one-line-installers.md`, `docs/specs/claude-config-dir.md`, `docs/specs/install-destination-selection-foundation.md`, `docs/adr/0037-install-selections-own-destination-cleanup.md`, `GLOSSARY.md` if terms change, CLI help and a changelog fragment. Before writing Tickets, use a Term sweep to confirm the complete list and keep historical behavior distinguished from current behavior. Explicitly describe the limits until #568 lands.

## Testing decisions

Test at the install CLI and disk boundary with isolated home and Project directories. Cover first-use empty choices, saved-choice confirmation, new and legacy candidates, multiple Claude directories and explicit paths, dedicated Copilot files, global/Project separation, one- and multi-target flags, explicit reuse, missing terminal, cancellation and dry-run. Test the actual POSIX pipe entry point and Windows PowerShell console behavior without network access using stubs. Assert selected files, removed marked files, recoverable edited backups, untouched unrelated files and unchanged records on cancellation or preflight failure.

Use real ACL and untrusted-principal fixtures on every claimed OS for writable parents, permissive ACLs, symlinks and reparse points, wrong owners, inherited permissions, filesystem types, missing backends and failure ordering. Include race/identity-change tests and validate no unrelated target is altered. Test path inputs with traversal, long names, control characters and aliases. Verify user-edited and legacy Skills and agents independently. Run the project's full Verify, static checks, package tests and applicable shell, PowerShell and workflow linters.

## Out of scope

Modifying `tds-factory update` to choose before npm, introducing Bootstrap-specific flags, or delivering the final two one-line workflows. Those are issue #568. Automatically removing unrelated files, installing Node or changing OS permissions for the user is also out of scope.

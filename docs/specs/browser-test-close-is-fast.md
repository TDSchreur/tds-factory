# Closing a browser test page does not wait out a deadline

## Spec

`close()` in `test/browser.js` sends `Browser.close` over the DevTools protocol and then waits with `waitUntil` for the Chromium process to exit, so that ChromeDriver deletes a profile nobody writes into (#561). In practice Chromium does not leave after `Browser.close`: it stays alive (process state `S`) for 8 seconds or more and exits about 50 ms after `DELETE /session`. The wait therefore always runs to its 5 second default deadline, once for each of the 140 `openPage()` calls, and `npm run test:browser` takes about 119 seconds although a page opens in about 0.4 seconds. Sending `SIGTERM` is not a fix: Chromium exits but stays a zombie child of ChromeDriver, which `process.kill(pid, 0)` still reports as alive, and a `scoped_dir` profile leaked in 1 of 3 trial runs. `close()` must reach the point where Chromium no longer writes into its profile without waiting out a deadline, and #561's invariant must still hold: no leaked `scoped_dir` directory and no browser process left behind. The change keeps every wait bounded, uses no fixed sleep and no longer timeout, and is chosen by measuring the candidates (an exit check that treats a zombie as gone, a different order of `Browser.close`, `DELETE /session` and the driver shutdown, or another signal that Chromium stopped writing) against #561's stress loop (8 browser sessions in parallel plus 24 busy loops, 0 leaked profiles in 320 sessions, run twice) and keeping the fastest safe one. A regression test asserts that `close()` returns well under the old 5 second wait with a generous upper bound, and `test/dashboard-teardown-browser.test.js` and `test/browser-teardown.test.js` stay green 30 times plain, under load and with `--test-concurrency=1`.

## Documents

The change touches `test/browser.js`, one test file and a changelog fragment in `changelog.d/`. `docs/development.md` and the reliable-tests guide are checked for a mention of the 5 second wait.

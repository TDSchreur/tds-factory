# The Dashboard checks and fixes a PR but never merges

> Extends [ADR 0024](0024-the-user-can-grant-an-extra-check-loop.md): the user can also grant an extra loop together with a Follow-up Fix.

The Dashboard had a Merge button on Done cards. Real pull requests are blocked by CI and review, so the button either failed or invited a merge that review had not cleared. What a user needs after Finish is to see what blocks the pull request and to send the agent back to fix it.

**The Dashboard never merges.** We removed the Merge button, its note, the merge and merge-checks routes, `prMerge`, `prCanMerge` and the PR provider's `merge` capability ([ADR 0020](0020-pr-providers-sit-behind-one-seam.md)). The user merges on the host, where CI and review apply. We considered keeping the button and gating it on green checks; it would still be a second, weaker gate next to the one the host owns.

**The Dashboard may start a scoped Follow-up.** A **Check PR** button does a fresh read of the pull request and the Run detail drawer lists its problems. For GitHub, one **Fix** button per Follow-up scope (`conflicts`, `checks`, `comments`) starts Follow-up for that scope only. This is a new guarded write route ([ADR 0017](0017-dashboard-write-routes-need-origin-host-and-a-session-token.md)): own Origin, own Host, the session token and the `updated` time the page showed. The same store operation backs `tds-factory run follow-up --id <id> --scope <scope>`, so the Dashboard has no rules of its own ([ADR 0006](0006-run-progress-goes-through-named-transitions.md)). Follow-up moves the Run to Build as a Rework, and the Dashboard path then sets the Run `waiting` with the reason "Follow-up Rework ready for an agent"; the card copies `/factory continue <run id>` for the user to give to an agent. The Dashboard starts no agent, as before. There is one Rework at a time, and a refusal because of the Run's state (worktree cleaned, uncommitted changes, head differs from the pull request head) is shown with how to resolve it and has no bypass.

**Grant and fix at the cap.** [ADR 0024](0024-the-user-can-grant-an-extra-check-loop.md) let the user grant an extra loop only to a Run waiting in Check. A Run at its loop limit in Follow-up has no such wait, and making the user find a different button first would block them. At the limit the Fix button reads "Grant extra loop and fix": one click raises `extra_loops` by one, writes the `extra-loop` event as before, and then starts the scoped Follow-up. It is still the user's act, one click per loop, with no ceiling; the command line cannot grant a loop. If the Fix is refused after the grant, the grant stands and is in the Event log.

**Untrusted text.** Check names, review comments and file paths come from the host. The drawer renders them as text, never as HTML, and Follow-up treats them as data, not instructions. In a `comments` Rework the agent changes code where a comment asks for it, lists in `follow-up-N.md` each comment it judged to need no change with the reason, and never posts replies or resolves threads on the host.

**Azure DevOps.** The Azure DevOps adapter reads the same problems as GitHub's (failing and pending checks, unresolved review threads and merge conflicts) and has `strictViewFlow` and `observeFlow`, so Check PR, the Fix buttons, "Grant extra loop and fix" and Follow-up work for it under the same rules: one scope and one Rework at a time, review text as untrusted data, and no reply or thread resolution on the host. Every `az` call is read-only; setup help for `az` is shown when it is missing or signed out. See the addendum in [ADR 0020](0020-pr-providers-sit-behind-one-seam.md).

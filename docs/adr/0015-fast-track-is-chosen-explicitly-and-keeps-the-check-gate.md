# The Fast track is chosen explicitly and keeps the Check gate

A bug fix or tiny change does not need the full interview, a multi-page Spec and several Tickets. We add a Fast track next to the Full track instead of a way to skip Stages: both tracks walk the same five Stages and the same named transitions of [ADR 0006](0006-run-progress-goes-through-named-transitions.md). Only the work inside Define, the Ticket count and the required Check axes differ. See the [Fast track Spec](../specs/fast-track.md).

The track is recorded in `run.json` as `track`. A missing value means the Full track, so older Runs keep their meaning. Only the named operation `run track`, which works in Define, sets it. `run start` and `run update` reject it. The Factory Skill calls it only after the user names the track or confirms Define's recommendation. We do not pick the track from the size of the work or a label, because a silent lighter Flow is exactly the failure to avoid, and the CLI cannot judge size anyway. The CLI therefore enforces what it can: it records the choice once, in Define.

The Fast track is lighter in Define and in the Ticket count, not at the gate. Define settles the work with one confirmation, writes a one-paragraph Spec and cuts exactly one Ticket; a bug goes through `diagnosing-bugs` first. Build refuses a Fast Run without exactly one Ticket. Check keeps Standards and Security as required axes on both tracks. The Spec axis may be `skipped` on the Fast track only, because a one-paragraph Spec leaves little to review against. Infrastructure keeps its existing rule. The Finish gate stays one rule for both tracks: only a clean Check goes on to Finish without asking, and anything else needs the user's accepted decision for the current head, as in the Check section of the Factory Skill.

Run metrics (see [ADR 0013](0013-run-metrics-preserve-observed-history.md)) fill the track dimension that ADR left open: `run stats` and the Dashboard Run detail show the track, and `run stats --all` totals each track, counting a Run without a track as Full. We read the track from the Run record rather than copying it into the metrics, so the two cannot disagree. The trade-off is that a Fast Run has less independent review of intent (no required Spec axis) in exchange for a shorter path, and that a wrongly chosen track is fixed by starting a new Run.

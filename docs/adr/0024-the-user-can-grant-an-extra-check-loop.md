# The user can grant an extra Check loop

A Run that has used its Check loops (four, or the lower cap the project set) and still has Blocking findings stops and waits for permission to continue to Finish. The user may want one more Rework instead ([milestone v0.6.0](https://github.com/TDSchreur/tds-factory/milestone/2), Dashboard item D4). The limit exists so that a Run does not loop for ever on an agent's own judgement, so the way past it must be the user's own act.

**The limit moves, the count does not.** The Run record gets `extra_loops`, a whole number from 0 (absent means 0). `loopCap` becomes the frozen cap, never above the Factory maximum of four, plus `extra_loops`. Every place that stops a Rework already asks `loopCap`: `run rework`, Follow-up and the Dashboard chip, so they follow without a change, and the chip reads "loop 4/5". We did not lower or reset `check_loops` to make room, because the count is what [Run metrics](0013-run-metrics-preserve-observed-history.md) report. The record validation no longer caps the stored count at four; the Rework operation enforces the cap.

**A named store transition, not a command.** `grantLoopRun` is in the Run store like the other transitions ([ADR 0006](0006-run-progress-goes-through-named-transitions.md), [ADR 0012](0012-run-store-is-split-by-seam.md)). It runs under the Run lock and refuses unless the Run is in Check, waits on the user and has reached `loopCap`. It adds one to `extra_loops`, sets the Run to running with the waiting fields cleared, and, through the usual change path, appends `released` and `extra-loop` events to the Event log ([ADR 0021](0021-run-record-model-last-seen-and-event-log.md)). `extra_loops` is a gated field, so `run update` refuses it. There is no `tds-factory run` command for it, on purpose: the command line is what agents use.

**The Dashboard route is the way in.** `POST /api/runs/<id>/extra-loop?updated=<time>` passes the same guard as every write ([ADR 0017](0017-dashboard-write-routes-need-origin-host-and-a-session-token.md)): own Origin, own Host and the session token. `updated` must equal the Run record's time the page showed, so a click on an out-of-date page is refused. One click is one loop and there is no ceiling or confirmation phrase: it is the user's decision each time.

**What this does not stop.** The token keeps other web pages and callers without it out. An agent that can run shell commands could read the token from `/api/info` and call the route, as it could for Accept. We state this in the docs instead of claiming a guarantee; the Factory cannot force an agent that ignores its Skill (see `docs/capabilities.md`). The same agent could edit `run.json` and set `extra_loops` itself, as it could set `check_loops` or a verdict: the Run record is a plain file and the Factory trusts it, as it always has. A claim that "an agent cannot grant itself a loop" therefore holds for a compliant agent that uses the commands, not for one that edits files. The grant is always in the Run record and the Event log, so it can be seen afterwards, and a raised `extra_loops` without an `extra-loop` event is the sign of an edit.

**Hand-off.** As with Accept, the Dashboard records the decision and the user then tells the agent in the chat. The Skill says that a limit raised since the agent asked is the user's decision to go back to Build once more, so the agent runs `run rework` and does not ask again for permission to continue to Finish.

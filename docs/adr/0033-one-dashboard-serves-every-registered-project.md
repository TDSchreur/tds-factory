# One Dashboard serves every registered Project

A user who works on several repositories at once had to start one Dashboard per repository, each on its own port derived from the repository path, and keep one browser tab per Dashboard. We decided that one Dashboard serves every Project in the per-user Project registry, with a Project row per Project. See the [Spec](../specs/multi-project-dashboard.md).

The Project registry is `projects.json` in the user's Factory config folder, outside every repository. It holds paths only. A Project joins it when a Run starts in it or when `tds-factory dashboard` runs there, always as the main checkout, and the page can only remove a Project, by the id the registry already holds. Adding takes a path, and ADR 0017 keeps paths out of write routes, so adding stays in the CLI. Registering is best-effort: a failed write is a warning and never stops a Run. Missing folders are shown in one summary row with per-Project cleanup and a bulk cleanup action, instead of being pruned, so an unmounted drive loses nothing.

One server listens on port 4300 and falls back to a free port when it is busy. The first `tds-factory dashboard` runs it in the foreground; later calls from other repositories only register their repository and print the URL. The server writes its pid, port and Factory version to a state file next to the registry, and a later call trusts it only after `/api/info` answers. An older Factory version is reported and never stopped. An explicit `--port` still starts a standalone server that neither reads nor writes the state file.

Routes name the Project: `/api/projects/<id>/runs/<runId>`, where the id is a short hash of the main checkout path, so equal Run ids in two Projects never collide. The guard of ADR 0017 is unchanged: Host, Origin and one Session token per server process, and a write only reaches a Project that is in the registry. Each Project keeps its own Run store, PR provider and PR status cache, so GitHub and Azure DevOps Projects sit side by side. Run records are polled for every Project; PR status stays lazy and is fetched only for visible cards.

We considered one Dashboard process per repository with a separate index page, a scan of a root folder for `.factory/runs`, and a detached background daemon with a `stop` command. The index page keeps one tab per repository, the scan is slow and finds repositories the user does not care about, and the daemon adds process management the Factory does not have today. The cost of the chosen design is that the first terminal must stay open, and that the server now serves many Run stores, so every handler has to take a Project instead of assuming one.

## Update 2026-11-03

The Dashboard keeps serving its own Project while the registry does not hold it (for example after a failed registry write). `DELETE /api/projects/<own-id>` for that case returns HTTP 409 with a message that there is nothing to remove from the registry, while any other unknown id stays HTTP 404. Cleanup of missing Projects is now `DELETE /api/projects/missing`, which removes only entries whose folders are still missing at request time and leaves entries whose folders returned.

# PR providers sit behind one seam

Four modules called the `gh` command directly: the Dashboard (merge, checks, state), Run clean-up, Follow-up and Run repair, each with its own parsing and its own copy of the GitHub URL and remote patterns. [Issue #276](https://github.com/TDSchreur/tds-factory/issues/276) puts every hosting call behind one module so a second host (Azure DevOps, planned for v0.6.0's PR support) is one more adapter, not four edits.

`src/pr-provider.js` is the seam: `providerFor(url)` returns the adapter that handles a PR link, or nothing, and `remoteRepo(remote)` returns the adapter and the owner and name that a git remote URL points at. An adapter exports `name`, `matches(url)`, `repoOfRemote(remote)` and the operations its callers use. `src/pr-github.js` is the only adapter and the only file that runs `gh` (a test pins this): it holds `view` and `viewAsync` (state and head), `stateAsync`, `checksSummary`, `merge`, `listByHead` for Run repair, and Follow-up's GraphQL observation (`strictView`, `observe`). Callers keep their own decisions (what an unreadable PR means for clean-up, for Follow-up or for the merge button) and their injection points for tests (`prState`, `prMerge`, `prInfo`), so behavior, CLI output, the Run record and the Dashboard API do not change. The one visible difference: a remote URL is now read by one pattern that accepts `http://`, `ssh://` with or without `git@` and `git@host:` forms, where the Dashboard and Run repair each accepted a slightly different subset.

We considered an object-per-host with every operation returning a common shape, but the callers need different guarantees (a clean-up must tolerate an unreadable PR, Follow-up must not), so the adapter returns what the host says and the caller judges it. The second adapter will show whether the interface needs more shared types. See ADR 0006 and ADR 0012 for the Run store these modules sit behind and [GLOSSARY.md](../../GLOSSARY.md) for **PR provider**.

**Addendum (PR status).** The adapter also has `statusAsync(url)`, which the Dashboard uses to show a Run's PR status ([issue #345](https://github.com/TDSchreur/tds-factory/issues/345)). One `gh pr view` call is parsed by `parseStatus` into a common shape (`state`, `draft`, `checks`, `merge`, `review`) and a failure carries a `reason` (`gh-missing`, `not-signed-in`, `rate-limited` or `error`). Unlike the other operations it returns a normalised shape, because the Dashboard only displays it; the second adapter will show whether that shape fits Azure DevOps.

**Addendum (Azure DevOps, [issue #365](https://github.com/TDSchreur/tds-factory/issues/365)).** `src/pr-azure.js` is the second adapter and the only file that runs `az`. It matches `https://dev.azure.com/<org>/<project>/_git/<repo>/pullrequest/<id>` and reads a PR with `az repos pr show` and `az repos pr policy list`, both read-only, into the same `statusAsync` shape; it also has `stateAsync` and `view` for the Done Stage and Run clean-up. Unlike `gh`, `az` is asked for the PR by id within an organisation, so the adapter checks that the PR's repository and project are the ones named in the link before it trusts the answer. Failures carry the reasons `az-missing`, `az-extension-missing`, `az-not-signed-in`, `rate-limited` and `error`.

The adapter has no `merge`, `viewAsync`, `checksSummary`, `strictView`, `observe` or `listByHead`. We did not add stubs that throw: the seam gets `can(url, operation)`, and a caller that uses an operation not every adapter has asks first. The Dashboard views carry `prHost` and `prCanMerge`, the Merge and merge-checks routes answer 409 for a host without them, Follow-up refuses with "Follow-up does not support Azure DevOps yet", and Run repair names the origin as one it cannot reconcile. The common status shape fitted Azure DevOps without change, except that reviewer policies are read as review state and not as checks. Merging and Follow-up on Azure DevOps are left for a later decision: they write, and the tests record real output only from the sandbox repository.

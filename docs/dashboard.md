# The Dashboard

`tds-factory dashboard` serves the `.factory/` folder of every registered Project, which includes the main checkout of the current repository (from any subfolder or linked worktree), on 127.0.0.1. Delete is available for individual Runs in every column. Stop the Run's agent before deleting an unfinished Run. Deletion removes the Run history and its Factory-created worktree, preserving its branch and linked Tickets, PRs and Specs. Adopted worktrees are left alone. If the worktree has uncommitted changes, including untracked files or changed submodules, a separate confirmation offers to permanently discard them and remove the worktree. Cancelling preserves the Run. Git or storage failures also preserve the Run and show the cause. Delete all is limited to Done Runs and asks separately about each dirty worktree.

Without `--port`, one Dashboard is shared by every repository ([ADR 0033](adr/0033-one-dashboard-serves-every-registered-project.md)). It listens on port 4300, or on a free port when 4300 is busy, runs in the foreground of the first terminal and writes its pid, port and Factory version to `dashboard.json` next to the Project registry. A later `tds-factory dashboard` in another repository registers that repository, prints the URL with `?project=<id>` and exits; it trusts `dashboard.json` only after the server answers `/api/info` with the same pid. Two calls that start at the same moment end up on one server: the one that loses the bind reuses the winner. A running Dashboard of an older Factory version gets a warning and is never stopped. `--port` starts a separate Dashboard on exactly the port you give; it neither reads nor writes `dashboard.json` and registers nothing. `/api/info` says `shared: true` only for a Dashboard backed by the registry; a call that finds anything else on port 4300, such as a `--port 4300` Dashboard, treats the port as busy and starts its own Dashboard on a free port.

The Project registry is `projects.json` in the Factory config folder (`$XDG_CONFIG_HOME/tds-factory` or `~/.config/tds-factory` on Linux, `~/Library/Application Support/tds-factory` on macOS, `%APPDATA%\tds-factory` on Windows; `TDS_FACTORY_CONFIG_DIR` overrides it). It holds the main checkout paths of the Projects that started a Run or ran `tds-factory dashboard`, also when that happened in a Run worktree. A registry that cannot be read is treated as empty with a warning and kept as `projects.json.corrupt`; one that cannot be written is a warning and never stops a Run. Every change to it (a Project joining or being removed) holds a lock file, `projects.json.lock`, so two processes cannot overwrite each other's change; lock ownership is tied to a per-process token, and stale-lock takeover is guarded by a separate tokenized `projects.json.lock.takeover` file, so only one process can verify and remove a stale lock before taking it. A lock older than ten seconds is stale; a lock that stays held for five seconds is a warning and that change is not saved. On Windows, a lock file that another process just removed can still be delete pending and refuse creation with `EPERM`, `EACCES` or `EBUSY`; that counts as held and is retried within the same five seconds, while on other hosts those errors are real and end the change with a warning. The registry and lock files are written owner-only (`0600` files in a `0700` config folder). If the config folder already exists, non-Windows hosts tighten it to `0700` (symlinks are left unchanged). The server reads the registry on every request, so a Project added by a later `tds-factory dashboard` appears without a restart, and it serves every Project in it, each with its own Run store, PR provider and PR status cache, so GitHub and Azure DevOps Projects sit side by side. A Project whose folder is gone is reported as missing, never dropped. While the registry does not hold the Project the server was started for (for example after a failed registry write), the server serves it too and still prints a `?project=<id>` URL for the main checkout. When registration fails because of an id collision, the CLI prints the plain Dashboard URL (no `?project=`) and warns about the collision. A server started with `--port` has no registry and serves only its own Project. A Run id is only unique within a Project, so every Run route names the Project by its id (a 12-character hash of the main checkout path); collisions are warned and an existing id is kept unchanged.

Only a strict semver from `/api/info` is trusted as a Dashboard version. The probe reads at most 64 KiB of `/api/info`, and a version longer than 64 characters is treated as unknown.

The header shows the serving Factory installation's version beside the logo, including when there are no Runs. This is the same version printed by that installation's `tds-factory --version`.

## Project rows

The page has one sticky row of Stage headers and, under it, one Project row per Project in the Project registry, so Runs of different Projects never share a column. The Project name is the folder name, with the parent folder added when two Projects have the same name. Each Project row is a labelled region whose heading holds a toggle button (`aria-expanded`); it works with Enter and Space.

- **Collapse.** A collapsed Project row is one line with the Runs per Stage and a **N waiting** badge. The counts and the badge are those of all the Runs of the Project that the page shows: **Needs you** never changes them, while the older-Runs toggle does (Runs older than a week stay out of the counts until you show them, waiting Runs never do). The choice is saved per Project id in the browser (`localStorage`), so it survives a reload; blocked or unreadable storage only means it is not remembered. A Run that starts waiting never expands a Project row, and neither does **Needs you**. Opening a Run from a notification expands its Project row.
- **Order.** Project rows are in alphabetical order and stay put, however the registry is ordered. The Project row of `?project=<id>` (the link `tds-factory dashboard` prints) is first and expanded. Inside a Project row the cards keep the waiting-first order.
- **Global controls.** **Needs you (N)**, the older-Runs toggle and the Done card expansion work over every Project row. A Run is always shown with its Project: cards sit in its Project row, and Run detail says "Project: <name>". Selection, expanded Done cards and the focus after closing Run detail are kept per Project and Run id, so two Projects may use the same Run id. **Delete all** in the Done column of a Project row deletes only that Project's Done Runs.
- **Empty and missing Projects.** A Project without Runs is a collapsed Project row that says "No Runs". Projects whose folders are gone are grouped in one summary row with a warning, per-Project **Remove** buttons and **Remove all missing**. Remove asks first, then sends `DELETE /api/projects/<id>`; bulk remove sends `DELETE /api/projects/missing` and removes every Project still missing at request time. Both only remove registry entries and touch no folder or Run.
- **Notifications.** A browser notification is raised for every Project and names it: "Needs you in <Project>: <title>".
- **Header.** The pill beside the logo shows the Project the Dashboard was started in; with several Projects it shows "N Projects" and the names as its tooltip, and the tab title no longer carries one name.

At widths up to 1024 CSS pixels, the Dashboard shows one Stage at a time. Use the Stage buttons to switch columns; the Stage headers are replaced by these buttons and the Stage applies to every Project row. Each button shows the number of visible Runs over all Projects and flags those waiting for you; the Project rows stack and can be collapsed. The first view favors a waiting Run's Stage, then the first nonempty Stage. Your selection stays in place while the Dashboard refreshes or you change the older-Run filter. Wider screens show all six columns together.

Selecting a Run opens its detail as a modal drawer on the right, over a full-width Dashboard that stays visible behind a light backdrop ([ADR 0031](adr/0031-run-detail-as-a-modal-right-drawer.md)). Close it with the close button, Escape or a click on the backdrop; focus returns to the Run's card. While it is open the Dashboard is not available, so close it before selecting another Run. A confirmation opened from the detail appears above it, and Escape closes only that confirmation first. A refresh keeps the drawer open, and it closes when its Run is no longer shown. At widths up to 1024 CSS pixels the detail fills the screen instead, with **Back to stages**. The Dashboard fits every width without a horizontal scrollbar; only wide Markdown tables in a summary scroll inside their own area.

Each card carries a Track row (Fast or Full) in its facts list (a Run without a track is Full), and Run detail shows it too, with Stage time, Reworks, the causes of the Reworks and first-pass clean rate using the same calculations as `tds-factory run stats --id ID`. Time includes waiting and repeated visits; an active visit is labeled ongoing. Old or missing observations show `no data`. Cost is `not tracked`; tokens are tracked from the Agent session logs when they can be read (see below). See [Run metrics in the usage guide](usage.md#run-metrics) for the rate and totals.

When a Run's [token usage](usage.md#5-follow-runs-on-the-dashboard) is tracked, each Ticket on a card is a tile of two lines. The first line is the status and the Ticket link. The second line shows the fresh tokens and the short model names, biggest first; the active Ticket says "so far", and a Ticket not yet started has no second line. Hover over the second line or focus it with the keyboard to see input, cache read, cache write and output per model. Work after a Rework has a tile of its own, "Rework". Run detail shows the same figures as a table that fills the drawer, with the labels that `tds-factory run stats --id ID` prints. When the drawer is narrow (below about 32 rem), each row stacks: the row label first, then each figure with its column header. A Run whose usage is not tracked looks as before.

## Help and the first run

The **Help** button in the header opens a help panel: a dialog with short sections on the Stages, the Fast and Full track, what "Needs you" means, the Check verdicts (pass, fail, skipped) and Left open, and the actions Sync, Clean up, Accept Check, Grant extra loop, Split, Continue, Check PR and Fix. The text is static (`dashboard/help.js`) and uses the glossary's terms. The focus moves into the panel, Tab stays inside it, Esc or **Close** closes it and the focus returns to what opened it. On narrow screens it fills the screen.

When there are no Runs at all and at most one Project (none missing), a welcome card replaces the Stage columns. It shows how to start (`/factory` and what you want built), says that the Run appears here, and has a **How does this work?** link that opens the help panel. The card goes away as soon as a Run exists, and it does not appear when the Needs you filter merely hides every Run.

## Design

The Dashboard follows Fluent 2 ([ADR 0025](adr/0025-the-dashboard-adopts-fluent-2-through-design-tokens.md)): neutral surfaces, a brand blue accent, 14 px type, 4 px corners and soft elevation. `dashboard/style.css` starts with a layer of Fluent design tokens, named as Fluent names them (`--colorNeutralBackground1`, `--fontSizeBase300`, `--shadow4`, ...), taken from `@fluentui/tokens` 1.0.0-alpha.24 (`webLightTheme` and `webDarkTheme`). Every rule below the layer uses only those tokens; a test checks that no rule uses a literal colour and that every token is used. No font is shipped: the font list starts with Segoe UI and continues with the system fonts. To update the tokens, follow ADR 0025.

- **Themes.** Light, dark and System work as before: the theme selector sets `data-theme`, and System follows `prefers-color-scheme`.
- **Contrast.** Every text and background pair keeps at least 4.5:1, and borders, focus rings and the progress fill keep 3:1, in both themes. A unit test computes this from the token values and a browser test measures the rendered text. Pass, fail, quiet and waiting states also say so in text and symbols, never by colour alone.
- **Skip link.** The first Tab stop is a "Skip to the Runs" link, hidden until it has focus; Enter moves focus to the Dashboard. It is not shown while the welcome card replaces the Dashboard.
- **Focus.** Every control that can take keyboard focus shows a two-colour ring (an inner and an outer ring), so it shows on every surface in both themes. Keyboard focus is never hidden under the sticky page header or Stage headers: focused controls in the Dashboard scroll to just below them. The **Delete all** button of a Project row is named for its Project ("Delete all Done Runs of <Project>").
- **Reduced motion.** With `prefers-reduced-motion: reduce` the Dashboard has no transitions or animations.
- **High contrast.** With forced colours (`forced-colors: active`) the browser uses your system colours. The progress fill, the status dot, the primary and pressed buttons (also when hovered or pressed), the selected card and the focus ring are redrawn in the system highlight colours, and a waiting card also gets a 3 px double border. An abandoned Run has a dashed card in a muted surface, not faded text, so its text keeps the same contrast.
- **Narrow screens.** Up to 1024 CSS pixels the Stage navigation and the full-screen detail work as before, with 44 px touch targets. The six Stage columns fit from 1025 CSS pixels up without a horizontal scrollbar.

## Runs that wait on you

One definition of waiting is used everywhere: the Run's `waiting` flag in `/api/views`, which is true while its status is `waiting` or `waiting_on_human` is set and the Run is not done or abandoned. The card border, the banner, the filter, the sort, the tab title count and the browser notification all read it.

- A waiting card carries a banner that starts with a pause symbol and reads "Needs you, waiting 12 min: <reason>". The Run detail shows the same banner. It is text and a thick left border as well as colour.
- The wait age comes from the Run's event log: the latest waiting event, if nothing released the Run or changed its status after it. When the log cannot tell (an older Run, a damaged log or a wait older than the last 50 events), the banner shows no age and does not guess.
- The **Needs you (N)** button in the header filters every Stage to the Runs that wait on you. It is pressed while the filter is on, and a Stage without waiting Runs says so. The filter is not saved and does not change the tab title count.
- In each Stage, waiting Runs come first, the longest wait first.
- Paused Runs ("Verification unavailable", "Agent interrupted") keep their own line and are not waiting.

## Pull request status

A Run with a GitHub or Azure DevOps pull request in Finish, Follow-up or Done (and not abandoned) shows the status of that PR on its card and in its detail, read through the PR provider ([ADR 0020](adr/0020-pr-providers-sit-behind-one-seam.md)) with one `gh pr view` call, or for Azure DevOps with `az repos pr show`, `az repos pr policy list` and, for an open PR, the PR statuses (`az devops invoke` on `pullRequestStatuses`):

- The link to the pull request (on a card that is not Done; a Done card has its own link).
- For an open PR: **Checks** (passing, pending, none reported, or failing with the names of up to five failing checks), **Merge** (no conflicts, conflicts with the base branch, or unknown, which GitHub says while it still works it out), **Review** (approved, changes requested, review required, none yet) and **Draft**. A failing check and a conflict are also marked in colour, but always say so in text.
- A merged or closed PR shows no status lines: the state badge says it.

The status never delays the Dashboard. `/api/views` answers from a cache per PR link and starts the lookup in the background; the card says "PR status: checking..." until the first answer. An open PR is read again after a minute, a merged or closed one after ten minutes, and a failed lookup after half a minute. When `gh` or `az` cannot answer, the card says "PR status unavailable" with the reason and the fix (`gh` or `az` not installed, the Azure DevOps extension missing (`az extension add --name azure-devops`), not signed in (`gh auth login` or `az login`), rate limit reached, or the host could not be read) and a **Check again** button, which reads the status from the host again. The rest of the Dashboard is unaffected. The Check PR button does not use this status; it reads the pull request fresh.

### Azure DevOps

An Azure DevOps link has the form `https://dev.azure.com/<organisation>/<project>/_git/<repository>/pullrequest/<id>` (the older `visualstudio.com` form is not supported). The Azure CLI with its `azure-devops` extension and a signed-in user (`az login`) are needed, and every call only reads. The same lines are shown, taken from the PR, its policies and the statuses posted to it:

- **Checks** are the blocking policies that are not about reviewers (build validation, comment requirements, status checks) and the PR statuses (what outside CI posts to the PR): a rejected or broken policy and a status that failed or is in error are failing and are named, a running or queued policy and a pending status are pending. Of a status only the latest post per context counts, and a succeeded or not applicable one is no check. "Require a merge strategy" is not a check: it stays rejected until a merge strategy is chosen at completion.
- **Merge** is conflicts when Azure DevOps reports a merge conflict.
- **Review** is changes requested when a reviewer voted "rejected" or "waiting for the author", review required while a required reviewer has not voted or a reviewers policy is not met (a creator's own vote does not count unless the policy allows it), approved when someone approved.
- The Done Stage shows the PR as open, merged (completed) or closed (abandoned), and Clean up works after it is merged.
- The Dashboard offers no merge for any host. Check PR, Fix and Follow-up work for an Azure DevOps PR as for a GitHub one (see [Check PR and Fix](#check-pr-and-fix)).

The Factory never writes to Azure DevOps. The tests use output recorded from the sandbox repository `Kahoot` (`test/fixtures/pr-status/azure/`) and never call `az`.

## Check PR and Fix

**Check PR** appears on a Done Run with an open pull request and on a Run in Follow-up, on its card and in its detail. A click reads the pull request fresh (never from the status cache) and opens the Run detail on a "Pull request" section: its state and whether it is a draft, whether it has merge conflicts, each failing check by name with a link to its run, the pending checks and each unresolved review thread (file path, a shortened first comment and a link). Each list shows at most 50 entries and says how many more are not shown. A merged or closed pull request shows its state only. Azure DevOps shows the same: a failing build policy links to its build, a failing status to its target link, and a thread is unresolved when it is active or pending and a person wrote it (threads Azure DevOps creates itself for votes, pushes and policy updates are left out). When `gh` or `az` is missing or not signed in, the section shows the setup steps for that host (the same steps are in [Install](install.md)). Review text and check names are shown as plain text, and only `https:` links become links.

For a GitHub or Azure DevOps pull request the section has one **Fix conflicts**, **Fix checks** and **Fix comments** button next to the matching problem. A click asks first, then starts a Follow-up scoped to that one problem: the Run goes back to Build as a Rework and waits with "Follow-up Rework ready for an agent". The card then offers **Copy agent prompt**, which copies `/factory continue <run id>` for you to paste into the agent. Only one Rework runs at a time: while one is in progress the Fix buttons are disabled and say why. When Follow-up refuses (the Run worktree is cleaned up or has uncommitted changes, or its head differs from the pull request head) the button stays clickable and the dialog shows the reason and how to resolve it. At the Check loop limit the button reads **Grant extra loop and fix**: one click raises the limit by one (recorded as an `extra-loop` event) and then starts the Fix. The Dashboard never merges ([ADR 0034](adr/0034-the-dashboard-checks-and-fixes-a-pr-but-never-merges.md)).

## Progress on cards and in the Run detail

A card that is not Done shows how far the Run is, from the data in `/api/views` ([ADR 0021](adr/0021-run-record-model-last-seen-and-event-log.md)):

- A Ticket progress bar, when the Run has Tickets, with the finished and total count for screen readers.
- The activity line the agent last set.
- The model line. A model the Factory asked for reads "Model (requested): X, effort Y". Only a model the agent reported itself reads "Model (observed): X", with the requested one as its tooltip. Nothing is shown when no model is known.
- "Last seen N min ago", from the Run's `last_seen`. For a running Run it turns into a warning ("⚠ ... quiet", in text as well as colour) after 10 minutes. A Run that waits on you, is paused, finished or abandoned is never warned. A Run without `last_seen` shows no last-seen text.

The Run detail lists the Run's event log as a timeline, oldest first, with relative times: Stage changes, Tickets done, Verify start and result with its duration, waiting and release, other status changes and Reworks. When some lines of the log could not be read, a note above the timeline says how many, since the timeline is then incomplete. A Run without any of this data, such as one from an older version, shows none of these parts and nothing in their place.

The page is built with Preact and htm, committed in `dashboard/vendor/` (see `dashboard/vendor/README.md` for versions and how to update them) and loaded as ES modules, so there is no build step. See `docs/adr/0003-preact-htm-dashboard.md`.

| `POST /api/projects/<id>/runs/<run-id>/split?updated=<time>`                                                                                                  | Splits a Run in Build that waits for the Run size answer: it has the meaning of `run split`. The done Tickets stay, the others leave the Run and the `split` event is written. Unlike the command line, the Run then waits with "Split done: ready for an agent" and not on you (hand it to an agent with `/factory continue <run id>`). Answers 200 with the moved Ticket links, one per line as text, control and format characters replaced by spaces. Refuses like `continue`. Needs the session token.                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

## Actions

Cards carry buttons for the Dashboard actions. Each asks for confirmation, then shows the result or the reason it was refused.

- **Sync** appears on running Runs in Build and Check (a Run waiting on you, or paused, cannot change until it runs again). It rebases the Run branch onto the current default branch of `origin`. If the code or the base changes, the Evidence is cleared.
- **Accept Check** appears on a Check that waits on you. The confirmation lists the four verdicts. It records that you continue to Finish with a Check that is not clean, for the current code only; a new commit voids it. The Run is released from waiting. Then tell the agent in its chat that you accepted: it finds the decision recorded for the current head and moves on to Finish.
- **Grant extra loop** appears on a Run in Check that waits on you after it has used all its Check loops (four, or the lower cap the project set). The confirmation says what it does. One click allows one more Rework and raises the limit by one (the Check loops row then reads, for example, "4/5"); there is no ceiling, and you can grant another loop each time the Run waits at its limit again. The Run is released from waiting. Then tell the agent in its chat that you granted it: it sees the raised limit as your decision to go back to Build and does not ask again about Finish. The grant is in the Run record (`extra_loops`) and in the timeline. Only this button grants a loop: there is no command-line equivalent, and an agent cannot raise the limit with `run update`. As with Accept Check, the session token keeps other web pages out, but cannot stop an agent that reads the token from `/api/info` ([ADR 0024](adr/0024-the-user-can-grant-an-extra-check-loop.md)).
- **Split** and **Continue** appear next to **Copy agent prompt**, on the card and in the Run detail, for a Run in Build that waits for the Run size answer ([ADR 0035](adr/0035-build-waits-on-the-user-when-a-run-outgrows-the-size-limit.md)). Both ask first and send the `updated` time the page showed. **Split** keeps the done Tickets and moves the others to a new Run; the confirmation counts both. The result lists the moved Ticket links (a link that is not a safe URL stays text), or says "Nothing was left to move.". The Run then waits with "Split done: ready for an agent", and **Copy agent prompt** shows for it. **Continue** accepts the size, so it is not asked again, and the agent picks the Run up on its next step. A refusal (the Run changed meanwhile) shows the server message and reloads the page.
- **Check PR**, **Fix** and **Copy agent prompt** are described in [Check PR and Fix](#check-pr-and-fix).
- **Clean up** appears on a Done Run whose pull request is merged. It removes the Run worktree and branch and keeps the Run record.

Starting a Run stays in the agent: the Dashboard cannot start, resume or complete a Run. The one Rework it can start is a Fix, which an agent then takes over.

### Needs you notification

When a Run starts waiting on you while the Dashboard is open, the browser shows a notification, `Needs you: <title>`, with the reason. Runs that already wait when you open the page only count in the tab title. Press **Notify me** in the header to let the browser ask for permission; the button disappears once you have answered. Without notifications, the `(N)` in the tab title still shows how many Runs wait on you.

## Write routes

Every route that changes something (`DELETE` and `POST`) passes one guard before it does anything, and a request that fails it gets HTTP 403:

- the `Host` header is `127.0.0.1:<port>` or `localhost:<port>` (this applies to every route);
- the `Origin` header equals `http://<Host>`, so only this Dashboard page can write;
- the `X-Factory-Token` header holds the session token. The server makes the token when it starts and the page reads it from `/api/info`. It changes on every start, so reload an open page after restarting the Dashboard.

A write reaches only a Project the Dashboard serves: an unknown Project id is HTTP 404, a missing Project's Run routes are HTTP 409, and no request carries a path. Removing a Project (`DELETE /api/projects/<id>`) passes the same guard; when the id is the Dashboard's own Project but the registry has no entry, the route answers HTTP 409 because there is nothing to remove. Missing-entry cleanup (`DELETE /api/projects/missing`) passes the same guard and only removes entries still missing at request time ([ADR 0033](adr/0033-one-dashboard-serves-every-registered-project.md)).

The server sends no CORS headers and answers no preflight. See [ADR 0017](adr/0017-dashboard-write-routes-need-origin-host-and-a-session-token.md).

## Server modules

`startDashboard` in `src/dashboard.js` creates the server, applies the guard above, serves the static assets and returns `{ server, port, projectId, url, close }`. The Projects and their services (Run stores, in-flight set, PR views and PR seams) are in `src/dashboard-projects.js`. The routes are a table in `src/dashboard-routes.js` (method, path pattern and handler); the handlers are in `src/dashboard-handlers.js`, the PR status caches in `src/dashboard-pr-views.js` and `interpretRun` in `src/dashboard-view.js`. A request runs the guard first and then the matching handler. The git calls a request makes are async (`gitAsync` in `src/git.js`), so a slow git call does not block other requests, and so does the PR lookup of clean (`viewAsync` of the adapter). One action at a time runs on a Run of a Project, and its checks read the Run only after the guard is taken: a second delete, sync, clean, accept, extra-loop, continue, split or Fix (follow-up) on the same Run while the first is running is answered 409 "another action on this Run is already running". Actions on different Runs run side by side, and read routes are not guarded. If an accept fails and the Run cannot be put back to waiting, the cause is written to stderr and the answer is the accept's own error ([ADR 0030](adr/0030-one-flow-of-git-steps-runs-sync-for-the-cli-and-async-for-the-dashboard.md)).

## No merging from the Dashboard

The Dashboard never merges a pull request: CI and review apply on the host, so you merge there ([ADR 0034](adr/0034-the-dashboard-checks-and-fixes-a-pr-but-never-merges.md)). The routes `POST .../merge` and `GET .../merge-checks` do not exist: the POST answers 405 and the GET 404.

For how to read the cards, see the [usage guide](usage.md#5-follow-runs-on-the-dashboard).

The browser tab is titled `<project folder> · TDS Factory`, with `(N) ` in front while N Runs wait on you, so several Dashboards are easy to tell apart. The Dashboard serves `/favicon.svg` as the tab icon.

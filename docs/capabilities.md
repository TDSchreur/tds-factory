The rule to follow the Flow through (detailed instructions do not replace Define, no Stage is skipped, a refused transition is never worked around and `run.json` is never edited directly) is in the Skill and in every Stage agent of every target. It relies on the agent reading the Skill and its agent file: an agent that ignores Skills entirely cannot be forced. The Factory makes a bypass visible instead: the Run store refuses transitions without their prerequisites, `tds-factory run inspect` reports `stage-skipped` for a Run still in Define whose branch changes project files, and the `small-task-define` and `refused-transition` [eval](evaluation.md) scenarios grade the behavior.

The Check agents are given the diff and any command output by the coordinator, because they cannot run commands. Where the table says "Same", the Factory behaves identically and only the host's tool or sandbox setting differs.

The rule for an unavailable reviewer is in the Check section of [`skills/factory/SKILL.md`](../skills/factory/SKILL.md). The upstream steps the Factory overrides are listed in [`skills/factory/references/invoked-skills.md`](../skills/factory/references/invoked-skills.md), which the `## Invoked Skills` section of the Skill points to. [`test/capabilities.test.js`](../test/capabilities.test.js) checks the Review isolation row against the shipped Stage agent files.

## Default models per Stage

`tds-factory install` writes five Stage agents plus an interactive project-review agent per target (`factory-define`, `factory-build`, `factory-check`, `factory-finish`, `factory-follow-up`) next to the skills: `~/.claude/agents`, `~/.codex/agents` and `~/.copilot/agents` (`.github/agents` with `--project` for Copilot). `factory-define` does the Define Stage. The main agent stays the coordinator: it talks to you, owns the Run record and approvals, and runs the baseline Check reviews as three or four independent read-only agents, plus any applicable project reviews in independent source or interactive reviewers. `factory-interactive-check` is a separate reviewer, not a Stage agent. Each cell is model and reasoning effort; "default" means the session setting applies and "not set" means Copilot has no effort setting.

| Stage     | Claude         | Codex                   | Copilot                      |
| --------- | -------------- | ----------------------- | ---------------------------- |
| Define    | Sonnet, medium | `gpt-6.1-terra`, low    | `claude-sonnet-5.5`, not set |
| Build     | Sonnet, low    | `gpt-6-luna`, medium    | `gpt-5.3-codex`, not set     |
| Check     | Sonnet, medium | `gpt-6.1-terra`, medium | `claude-sonnet-5.5`, not set |
| Finish    | Haiku, low     | `gpt-6-luna`, low       | `claude-haiku-4.5`, not set  |
| Follow-up | Haiku, low     | `gpt-6-luna`, low       | `claude-haiku-4.5`, not set  |

Set a model for a project in `.factory/config.json` under `models` (see [Set project options](usage.md#set-project-options)); the coordinator passes it when it dispatches the agent. Editing the agent files still works for all projects. The Copilot agents set no `modelPolicy`, so a model your plan does not offer is replaced by the session model with a warning when you start the agent directly, but Copilot refuses to dispatch it as a subagent, which is how the Factory uses it. Check `/model` in Copilot CLI for the ids your plan offers and edit `model:` to match. Install updates agent files you have not edited and keeps ones you have; `--force` replaces those with the defaults too. Agent files from an install that predates this count as edited, so use `--force` once if you want the new defaults. Whether a model is available depends on your client, account and policy, and the client may substitute another or not report which one ran; the Factory reports such cases instead of assuming. The Copilot defaults were checked by dispatching against Copilot CLI 1.0.105 with one plan's model list, not against other Copilot environments or plans.

To see whether an agent follows the Flow, run the on-demand [agent evaluation](evaluation.md).

The extra Check loop is the one setting that is meant for the user alone ([ADR 0024](adr/0024-the-user-can-grant-an-extra-check-loop.md)). It has no command and `run update` refuses it, but an agent with shell access could still read the Dashboard's session token and call the route, as it could for Accept Check. The same goes for editing `run.json` and setting `extra_loops` directly, as for any other field of the Run record. The Factory cannot prevent that; the grant is always visible in the Run record and the timeline.

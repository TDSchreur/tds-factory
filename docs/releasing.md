# Publishing a Release

Day-to-day PRs go to `develop` and are squash-merged there. `main` holds only released code: it changes through a release PR from `develop`, and merging that PR publishes the Release. Publish when a useful group of changes is ready for colleagues.

1. Check that the changes you want are on `develop` and CI is green there. Choose the version, following [Semantic Versioning](https://semver.org/).
2. Branch from `develop` and, in one commit, set the version with `npm version <version> --no-git-tag-version` (it updates `package.json` and `package-lock.json`) and fold the changelog fragments with `node scripts/changelog.js release <version>`. The second command writes the new section from `changelog.d/` and anything under `## [Unreleased]`, and deletes the fragments. Open a PR to `develop` and squash-merge it.
3. Open a PR from `develop` to `main`. Wait for `ci-ok`, then merge it with a **merge commit**, not a squash or rebase, so `develop` and `main` keep the same history and the next release PR shows only new changes. The `main` ruleset must allow merge commits for this, and must not require the branch to be up to date: the merge commit is on `main` only, so `main` is always one commit ahead of `develop` and nothing needs merging back. Never commit to `main` directly, so that `develop` stays the only source of changes.
4. The merge starts the **release** workflow on `main`. It reads the version from `package.json` and fails if the tag `v<version>` already exists, so a release PR that did not raise the version stops there. Read-only jobs run the main suite on Node 24 and the latest LTS, plus mandatory browser tests. The publishing job waits for these checks, packs the release, and tests that exact tarball by installing the CLI and each Agent target into temporary directories. A failure prevents publication. Inspect the failed step, fix the problem on `develop` and release again, or, when the cause was temporary, select **Run workflow** on `main` in the **Actions** tab to retry.
5. Open **Releases** and check that the new version is marked Latest, the generated notes cover the intended changes, and its four assets are attached: `tds-factory.tgz`, `tds-factory.tgz.sha256`, `install.sh` and `install.ps1`. Colleagues install with the one-line commands in the README or the [install guide](install.md), and update with `tds-factory update`.

Never create a Release by hand (for example with `gh release create` or the GitHub UI): without all four assets it becomes Latest and the README install commands return 404. The release workflow ends by downloading each asset URL and comparing it with the file it built, and the `latest-release` workflow checks the same four URLs daily and whenever a Release changes, so a Latest Release without one of them shows up as a failed run.

The release is built from the `main` commit that the merge created. Do not push to `main` in any other way.
